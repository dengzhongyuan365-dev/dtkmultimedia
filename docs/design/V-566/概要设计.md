## 1. 背景、目标与非目标

### 1.1 背景

截图录屏（deepin-screen-recorder）在截图后的工具栏已具备"识别文字"（OCR）与"AI 截图"两项内容提取能力，但二者均不理解表格结构——前者逐行/逐词提取纯文本，后者做 AI 文本理解，均无法将截图中的表格还原为行列关系、合并单元格齐全的可编辑表格。

V-566 需求要求在 dtkmultimedia 源码包新增独立共享库 `libdtk6tablerecognizer`，封装"图片 → 表格"的完整本地离线识别流程，补上这一缺口的最底层能力。本需求仅交付库本身，不含截图工具入口集成与主程序跳转。

### 1.2 目标

- 交付独立共享库 `libdtk6tablerecognizer`，与 `libdtk6multimedia`、`libdtk6multimediawidgets`、`libdtk6ocr` 同级，随 dtkmultimedia 源码包打包。
- 输入一张含表格的图片，完全在本地离线识别出表格结构（行、列、合并单元格）与每个单元格内文字。
- 支持有线表格（带边框线）与无线表格（仅靠文字对齐形成）两种形态。
- 输出 HTML 表格、Excel（`.xlsx`）及结构化单元格数据（`QList<DTableCell>`）。
- 库自包含 SLANet_plus ONNX 模型（~7.4MB），OCR 复用同仓库 `libdtk6ocr` 的 PP-OCRv5 能力。
- 支持 arm64、x86_64、loong64 三架构（UOS），GPL-3.0+ 兼容。
- 提供异步调用接口与超时控制，避免阻塞调用方 UI 线程。
- 提供主模型不可用时的自动降级路径（OpenCV 有线表格检测）。

### 1.3 非目标

- 不含截图工具入口集成：不在 deepin-screen-recorder 截图工具栏增加"表格识别"按钮，不改动现有"识别文字/AI 截图"流程。
- 不含贴图（pin）程序集成：不在贴图窗口增加表格识别入口。
- 不含主程序跳转/交互设计：用户在截图工具中如何触发、结果如何展示，均属后续独立需求。
- 不含在线/云端识别：只做本地离线。
- 不含对扫描件/PDF 等非截图场景的专门优化（以截图场景为主）。

## 2. 现状与问题

### 2.1 产品现状

| 能力 | 实现方式 | 表格结构支持 |
|------|----------|------------|
| 识别文字（OCR） | 截图工具栏"识别文字"按钮 / 贴图窗口 Alt+O，通过 DBus 调用外部 `com.deepin.Ocr` 应用 | 否，仅逐行/逐词纯文本提取 |
| AI 截图 | 交给 `com.deepin.copilot` 做解释/总结/翻译/问答 | 否，AI 文本理解，不产出结构化表格 |

### 2.2 核心问题

用户无法把截图里的表格"还原成可编辑的表格"（行列表格/Excel）。表格会被识别成一堆散落文字，行列关系、合并单元格全部丢失。

### 2.3 代码现状

- dtkmultimedia 仓库现有三个同级库：`libdtk6multimedia`（`src/multimedia/`）、`libdtk6multimediawidgets`（`src/multimediawidgets/`）、`libdtk6ocr`（`src/ocr/`）。
- `src/CMakeLists.txt` 当前内容仅三行 `add_subdirectory`，分别引入上述三个库。
- `libdtk6ocr` 已含 PP-OCRv5 插件 `PaddleOCRAppV5`（`src/ocr/ppocr/ppocrv5.*`），插件名 `PPOCR_V5`，模型在 `src/ocr/dtkocrmodels/v5/`，安装到 `/usr/share/libdtk6ocr/dtkocrmodels/v5/`。其公开 API `Dtk::Ocr::DOcr` 提供 `loadPlugin` / `setImage` / `analyze` / `textBoxes` / `charBoxes` / `resultFromBox` 等方法。
- 全仓库检索未发现表格结构识别/HTML 表格/Excel 导出/SLANet/ONNX 相关实现，确认该能力为全新缺口。
- debian 打包已有 `libdtk6ocr` / `libdtk6ocr-dev` 二进制包定义；`misc/` 已有 `dtkocr.pc.in`、`dtkocrConfig.cmake.in`、`qt_lib_dtkocr.pri.in` 模板。

├── include/
│   └── dtktablerecognizer/     ← 新增公开头文件

### 3.2 库内部模块边界

| 模块 | 职责 | 对外暴露 |
|------|------|---------|
| `DTableRecognizer` | 公开 API 门面，`QImage → DTableResult`，管理异步与超时 | 是（公开头文件） |
| `OrtInferenceEngine` | ONNX Runtime C++ API 封装，仅加载 SLANet_plus ONNX | 否（内部） |
| `TableStructureDetector` | SLANet 前后处理 C++ 移植（~800–1200 行），输出表格结构 | 否（内部） |
| `DtkOcrWrapper` | 封装 `Dtk::Ocr::DOcr` 调用，`loadPlugin("PPOCR_V5")` 显式加载 V5 | 否（内部） |
| `CellTextMapper` | TextBox → Cell 坐标映射（center-point + IoU） | 否（内部） |
| `HtmlTableBuilder` | 结构化单元格 → HTML 表格 | 否（内部） |
| `XlsxTableBuilder` | 结构化单元格 → Excel（libxlsxwriter） | 否（内部） |
| `Img2TableFallback` | OpenCV 降级路径，有线表格线检测 | 否（内部） |
| `models/` | SLANet_plus ONNX 模型文件，安装到 `/usr/share/libdtk6tablerecognizer/models/` | 否（数据） |

### 3.3 依赖关系

```
                     DTableRecognizer (门面)
                    /        |          \
        TableStructureDetector  DtkOcrWrapper  Img2TableFallback
              |                   |                  |
        OrtInferenceEngine    libdtk6ocr         opencv_mobile
              |              (DOcr / PPOCR_V5)
        onnxruntime               ncnn + opencv_mobile
              |
        SLANet_plus ONNX
```

- **OCR**：通过 `Dtk::Ocr::DOcr` 公开 API 调用，`loadPlugin("PPOCR_V5")` 显式加载 V5，`setImage(QImage)` / `analyze()` / `textBoxes()` / `charBoxes(i)` / `resultFromBox(i)` 取结果。`DOcr` 内部已用 ncnn + opencv_mobile，新库不再重复。同源码包内可直接链接 `dtk6ocr` CMake target。
- **结构推理**：`OrtInferenceEngine` 封装 ONNX Runtime C++ API 加载 SLANet_plus ONNX；`TableStructureDetector` 移植前后处理。
- **Excel**：`XlsxTableBuilder` 用 libxlsxwriter 输出 `.xlsx`。
- **降级**：`Img2TableFallback` 用 opencv_mobile（仓库已用）做有线表格线检测。

## 4. 关键流程和跨模块交互

### 4.1 主识别流程

```
调用方 recognizeAsync(QImage)
  → [工作线程] DTableRecognizer 门面
    → TableStructureDetector.detect(image)
      → OrtInferenceEngine.run(SLANet_plus ONNX)  → 表格结构（行列、合并单元格 bbox）
    → DtkOcrWrapper.recognize(image)
      → DOcr.loadPlugin("PPOCR_V5") → setImage → analyze → textBoxes / charBoxes / resultFromBox
    → CellTextMapper.map(structure, ocrBoxes)
      → center-point + IoU 映射，将 OCR 文字框归入对应单元格
    → HtmlTableBuilder.build(cells) → HTML
    → XlsxTableBuilder.build(cells) → .xlsx 文件路径
    → DTableResult { success, html, xlsxPath, cells, source, errorMessage }
  → emit recognitionDone(DTableResult)
```

### 4.2 降级链

```
SLANet_plus(ORT) + dtk6ocr(PP-OCRv5)
  ↓ 主模型不可用 / ORT 加载失败
img2table(OpenCV 有线表格检测) + dtk6ocr(PP-OCRv5)
  ↓ 降级仍无法识别
返回失败（仅 errorMessage，无 UI）
```

降级触发场景：ORT 运行时不可用、SLANet 模型加载失败、无线表格检测置信度过低。降级路径仅对有线表格有效，无线表格在降级路径中无法识别，返回失败结果。

### 4.3 异步与超时

- `recognizeAsync` 在内部工作线程执行全部识别，避免阻塞调用方 UI 线程。
- 超时默认 10 秒，超时按失败处理（`success = false`，`errorMessage` 说明超时），避免调用方无限等待。
- `DOcr::analyze()` 为同步阻塞调用，须在工作线程运行 OCR。
- QImage 跨线程需注意深拷贝，确保图像数据线程安全。

### 4.4 跨模块交互边界

- 新库与 `libdtk6ocr` 之间仅通过公开 API `Dtk::Ocr::DOcr` 交互，不修改 `libdtk6ocr` 任何源码。
- 新库与 `libdtk6multimedia` / `libdtk6multimediawidgets` 无直接交互。
- 构建层面仅通过 `src/CMakeLists.txt` 追加 `add_subdirectory(tablerecognizer)` 一行接入。

## 5. 数据、接口、兼容性原则

### 5.1 公开 API 契约

```cpp
struct DTableCell {
    int row, col, rowSpan, colSpan;
    QRectF bbox;
    QString text;
};

struct DTableResult {
    bool success;
    QString html;
    QString xlsxPath;
    QList<DTableCell> cells;
    QString source;       // "SLANet_plus" 或 "img2table"
    QString errorMessage;
};

class DTableRecognizer : public QObject {
    void recognizeAsync(const QImage &image,
                        std::chrono::milliseconds timeout = 10s);
signals:
    void recognitionDone(const DTableResult &result);
};
```

### 5.2 数据模型

- **DTableCell**：单元格逻辑位置（行、列、跨行、跨列）+ 物理位置（bbox）+ 文字内容。
- **DTableResult**：识别结果汇总，包含 HTML 文本、Excel 文件路径、结构化单元格列表、识别来源与错误信息。
- **source 字段**：标识结果来自主模型（`"SLANet_plus"`）还是降级路径（`"img2table"`），便于调用方区分。

### 5.3 兼容性原则

- **纯增量新增**：不修改任何现有库的源码、公开 API 或行为。
- **构建兼容**：仅追加 `add_subdirectory` 一行，不影响既有库编译。
- **打包兼容**：新增独立二进制包，不影响既有包。
- **运行时兼容**：新库为可选依赖，未安装不影响既有库运行。
- **API 稳定性**：首次交付为 v1 契约，语义改变时递增版本。

## 8. 安全、隐私、性能、可观测性要求

### 8.1 安全与隐私

- **完全离线**：全程不联网，模型与 OCR 引擎均随库本地提供，不发起任何网络请求，不传输用户图片数据。
- **本地处理**：图片数据仅在调用方进程内存中处理，不落盘、不外传（Excel 输出文件由调用方指定路径，库不主动上传）。
- **无权限提升**：库不申请额外系统权限，不访问网络、不访问文件系统外的资源（仅读写调用方指定的 Excel 输出路径）。

### 8.2 性能

- **单图推理**：v1 PoC SLANet 结构检测平均 0.648s/图，OCR 98.5% 精度，映射 100%。Phase 0 需引入标准基准复核。
- **超时控制**：默认 10 秒，可由调用方通过 `recognizeAsync` 参数调整。超时按失败处理，避免调用方无限等待。
- **线程模型**：异步执行，不阻塞调用方 UI 线程。

### 8.3 可观测性

- **结果来源标识**：`DTableResult.source` 字段标识主模型（`"SLANet_plus"`）或降级（`"img2table"`），便于调用方区分与诊断。
- **错误信息**：失败时 `errorMessage` 提供可读错误说明（超时、模型加载失败、无表格、降级失败等），由调用方决定如何提示用户。
- **不自带日志/UI**：库不输出日志到文件，不弹出 UI，不直接与用户交互。日志与错误展示由调用方负责。

## 9. 验收原则、待确认事项和变更记录

### 9.1 验收标准

1. 传入清晰的有线表格图片，库输出结构正确的 HTML 与 Excel，行列、合并单元格与原文一致，单元格文字识别准确。
2. 传入无线表格图片，库输出结构正确的 HTML 与 Excel，准确率不低于基线（PoC 无线结构正确率约 88%；Phase 0 需用标准基准 PubTabNet TEDS 与真实截图复核并定阈值）。
3. 传入不含表格的普通图片，库返回"未识别到表格"类失败结果，不崩溃、不误产出空表格。
4. 库支持设置超时，超过超时时间（默认 10s）的识别能被中止并返回失败结果。
5. 主模型不可用时能自动降级到有线表格识别（img2table），降级路径可用且结果可用。
6. 库完全离线运行，识别过程不产生任何网络请求。
7. 库在 arm64、x86_64、loong64 三架构下均可正常编译与运行。
8. 库随 dtkmultimedia 源码包打包，模型文件安装到系统目录，调用方无需额外下载模型。
9. 提供可被第三方调用的稳定公开接口（图片输入 → HTML/Excel/单元格数据输出）与对应 pkgconfig 文件。
10. 所有依赖许可证与 GPL-3.0+ 兼容。
